# A1 预处理内存修复说明（重要：使用本实验前必读）

> 2026-11-03 ｜ 修复 commit：`152c7d1`（分支 `five-terrain-controls` / `five-terrain-supplementary`）
> 影响范围：仅 `three_stage`（A1/M0 架构）的高速预处理阶段；`single_gnn` 与各 baseline 不经过此路径。

## 一、提醒：我们对预处理代码做了修改

`main.py` 标准路径里的 `build_pipeline_inputs()` 原先会物化**稠密 `[N, K]` access 距离矩阵**
（N=顶点数，K=高速/边界节点数）。在五地形规模下这是不可行的：

| 地形 | N | K | 稠密矩阵体积 |
|---|---|---|---|
| BH_high | 1,318,844 | 33,531 | **≈165 GiB** |
| 其余三图同量级 | — | — | 上百 GiB |

32GB 内存的机器在 A1 预处理阶段直接 `numpy._ArrayMemoryError` 崩溃（2026-11-03 首次本机运行
时发生，见 `logs/BH_high_A1_no_res_s42_100ep.log`）。**归档 M0 云端当年能跑，不是因为稠密矩阵
合理，而是它用了自己的 runner：只存每节点最近 16 个高速入口**（其日志为证：
`topk access tables ... shape=(1318844, 16) 84.4MB`）。

因此我们把标准路径对齐到 M0 的实际口径：**流式滚动 topk-16 轻量视图**，替代稠密矩阵。

## 二、修改清单

| 文件 | 修改 |
|---|---|
| `build_highway.py` | 新增 `AccessTopK` / `_AccessRowProxy` 只读视图（每节点仅存最近 16 个高速入口的距离与 local 索引；未存条目语义 = inf）；`build_pipeline_inputs` 的流式 Dijkstra 循环改为滚动维护 topk-16（K ≤ 16 的小图保持原稠密路径不变）；行视图越界抛 `IndexError`（保证 `enumerate`/`sorted` 等序列迭代协议正常终止） |
| `preprocess.py` | `precompute_nearest_k` 增加 AccessTopK 快路径（视图已按距离升序，直接切片）；`edge_index` 构造改为先 `np.stack` 再转 tensor（仅消除 PyTorch 性能警告，张量内容逐元素等价） |
| `scripts_local/test_accesstopk_regression.py` | 新增回归测试（见第四节），可随时重跑验证 |

**未改动**：图构建、四叉树分区、边界提取、Dijkstra 本身、transit 边生成、`highway_pair_dist`、
模型/训练/评估全部逻辑。

## 三、为保证与归档 M0 一致性做了什么

1. **口径锚点逐项核对**（M0 日志 vs 本机运行）：`|V|=1318844`、`leaves=64`、`K=33531` 完全一致
   ——图构建与分区链路在修改前后是同一套代码，未受影响。
2. **存储口径对齐 M0 runner**：topk-16、float32、按距离升序、未存条目按 inf——与 M0 日志中的
   `(1318844, 16) 84.4MB` 逐字节对应（1318844×16×4B = 84.4MB）。
3. **消费侧全清单审计**：`access_dist` 的所有使用点（`precompute_nearest_k(k_max=16)`、
   逐样本入口选取 top-3、access 距离特征、baseline 兜底行扫描）**没有任何一处读取 top-16
   之外的条目**——topk 截断对消费侧不可见。
4. **回归测试四层验证**（`python -u scripts_local/test_accesstopk_regression.py`，全绿）：
   ① 随机矩阵（含不可达 inf、整行不可达、批大小非约数的 flush 边界）：流式滚动 topk 与
   稠密矩阵+argpartition 的 top-16 **距离序列逐行相等**；
   ② 行视图 `getitem`/`len`/`enumerate` 协议（覆盖 baseline 兜底路径）；
   ③ `torch.save/load`（pickle）缓存往返；
   ④ 真实网格 `data/sample_terrain.off`（N=793, K=593）端到端：强制稠密 vs 强制 topk 各跑一遍
   完整 `build_pipeline_inputs`，**transit 边集完全一致**且 topk 距离一致。
5. **A1 跑完后的两道终验锚点**（留给后续执行者复核）：
   - transit 边数对比 M0 日志锚点 `highway tk8 edges=338456`（注意有向/无向计数口径）；
   - 金标准：用**归档 M0 权重**（`BH_high_ours_s42_100ep.pt`）+ 本修复生成的预处理缓存 +
     归档 test 划分，经 `scripts_local/score_checkpoint.py` 推理，应复现 test MRE ≈ **0.9032%**。

## 四、为什么这只是内存优化、没有其他副作用

- **数学等价**：「稠密矩阵 + 事后 argpartition 取 top-16」与「流式滚动维护 top-16」产出的是
  同一组数（同一平局规则下逐元素相等）；Dijkstra 是精确最短路，float64 计算 float32 存储，
  两条路径相同。transit 边生成用的是每个源的**完整**距离向量（流式循环里逐源可用），
  不受 topk 截断影响。
- **内存账**：165 GiB → topk 表 168MB + 归并临时约 1GB + Dijkstra 工作内存约 2.7GB，
  峰值约 10GB，32GB 机器安全。
- **唯一理论差异源（诚实声明）**：
  - 完全等距的并列项顺序可能不同——但 M0 自己的 runner 也有其任意平局顺序，属同一等价类，
    距离值不受影响；
  - 不可达节点的 padding 语义（-1/inf）——地形网格连通，实际不存在；
  - 训练阶段的 GPU 浮点非确定性与本修复无关（A1 是"同协议重训"，test MRE 落在 M0 附近即合格）。
- **小图行为不变**：K ≤ 16 时自动走原稠密路径，`sample_terrain` 等小图/单测语义零变化。

## 五、对实验结论的影响

A2/A3/NeuroGF/LiteGE（single_gnn 及 baseline 路径）**不经过本修改**，其已入库结果
（`outputs/results/*_s42_100ep.txt`）与本修复无关。A1 重训结果应以本修复后的预处理为准，
与归档 M0 对比时遵循"同协议重训"口径（允许训练随机性带来的小幅波动）。
